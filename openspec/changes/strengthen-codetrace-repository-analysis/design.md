# Design

## Context

动机见 proposal.md。当前应用为单进程 Python 3.12 CLI，LangGraph model/tools/validate/repair 四节点已有严格证据和预算机制。repository.py 的 search_code 按稳定文件顺序执行区分大小写的字面量搜索，默认30条命中、最多500候选文件；没有索引、语法解析或排名。graph.py 使用全局 TOOLS，并在工具之后重新计算有界仓库指纹。evaluation.py 的v1仅允许固定双语言夹具，离线脚本直接使用标注片段安排读取，不能度量自主定位能力。

截至本次规划，已有一次 DashScope qwen3.8-27b 的真实跨文件记录；在途 deliver-codetrace-analysis-mvp 的6.3/6.4未全部完成。该变更的旧背景描述不能替代当前状态。用户已确认只细化分析阶段，编程阶段保留路线图。README存在用户未提交修改，本次不纳入规划提交。

本设计跨越工具集合、数据版本和评测协议，并增加解析依赖，因此需要独立设计文档。

## Goals / Non-Goals

**Goals:**
- 相同分析程序可运行于独立陌生仓库，禁止按基准仓库名、预期文件或题目ID分派专用逻辑。
- 首先支持Java/Spring Boot的源码导航，Python作为第二种真实验证语言；其他允许后缀仍可文本检索。
- 将索引/导航定位与read_file证据登记分离，复用既有校验和失败路径。
- 以固定版本、两种检索模式和显式人工审核建立可复现对照，不把小样例和真实语义能力混算。

**Non-Goals:**
- 完整类型推断、运行时调用图、Spring容器解析、事务正确性证明、框架代码执行。
- 分析工具自动克隆仓库、下载依赖、执行构建或修改目标文件。
- 本次实现编程工具、补丁、终端、隔离容器、会话恢复、Web产品或向量检索。

## Decisions

### 1. 独立分析产品，先保持CLI边界

本阶段产品任务为入口定位、跨文件业务流程、配置追踪、异常处理和有依据的不足回答。Java项目是受测对象而非服务依赖；切换仓库只改变 --repo，无需修改CodeTrace。继续采用独立Python架构，不拆Java/Python微服务。

增加 --retrieval literal|indexed（默认literal），indexed在原四工具上增加 find_symbol、find_related_symbols、search_code_ranked。新增 --report PATH 导出Markdown。结果信封保持schema_version=1，新增信息放入可扩展trace记录；现有字段及严格模型不任意放宽。

替代方案：直接切换默认排序会破坏现有基线，立即上Web会把工作重心转移到产品交互。显式模式提供回退和公平对照，未来默认切换需另行评估。

### 2. 任务内索引，资源预算先行

新增 indexing.py 承担安全文件清单和内容快照；通过Repository既有路径检查及读取接口扩展获取字节计数，不自行使用无边界rglob。解析和排名分别放在 symbols.py、retrieval.py，工具适配仍经Repository.execute统一校验。每次analyse实例拥有自己的索引，不使用全局可变缓存、不写入目标仓库。

默认沿用2000文件、10000目录项和256000字节单文件，再加累计16MiB字节预算。每次打开前计算剩余额度，最多读取min(单文件上限+1,剩余总字节)，包括失败解码的读取量也计入；无法在剩余额度内确认完整文件时跳过并标partial，不索引截断文件。解析依赖实际读到的完整UTF-8内容；每个文件保存内容哈希、行文本、解析状态及轻量符号记录。

索引在第一次indexed工具请求时懒构建，由tools节点现有deadline约束；构建前后均检查deadline，遍历过程中定期检查取消信号，超时不继续调度。此协作式取消不能承诺OS层文件读取硬取消。长文件解析时保留单文件大小和任务时限约束。

清单摘要为按相对路径排序的文件哈希及覆盖参数摘要，index_id是任务实例标识。扫描预算、时间、跳过原因分别记录。构建时不把2000文件清单全文放入模型上下文，仅返回摘要与被选候选。

候选返回前重新安全读取并核对涉及文件的哈希（同一查询内去重）。变化时返回index_stale，失效该文件缓存；下一次查询重新读取/解析该文件，不无界自动重试。已登记的旧证据继续绑定旧快照。任务期间新增文件不自动发现，报告明确索引为初次清单；新任务重建清单。禁止依赖mtime相同就假定内容相同。

替代方案：SQLite持久索引需要失效、升级和清理策略；第一阶段先保证行为清楚，索引仅在当前任务复用。现有重复检测的全仓库指纹暂保留，测量其开销，不未经对照就改变已测试的重复语义。

### 3. 有限符号解析与关系候选

Java选择Tree-sitter和Java grammar，Python使用ast；新包版本通过Windows/Linux Python3.12的最小解析测试后锁定，不在规划阶段编造已验证版本。可选依赖安装方式避免literal模式因解析器不可用而不能运行：indexed配置检查给出明确缺依赖错误；完整开发快照与CI安装解析依赖。

Java提取package、import、class/interface/enum/record、构造器、方法、显式extends/implements、注解源码；Python提取模块、类、同步/异步函数、类方法、导入和显式基类。类和成员限定名按词法嵌套组合，保留签名和行范围。以源码字节位置转换行号，覆盖中文注释、CRLF、装饰器/注解、多行签名、重载及内部类。Java出现ERROR/MISSING节点或Python语法错误，整个文件符号标记parse_error并回退文本检索，避免半解析结果被当作准确声明。

symbol_id由相对路径、限定名、种类、签名及定义范围稳定生成，只用于导航，不能作为evidence_id。find_symbol输入name、kind、language、path、limit（默认10、最多20）；名称精确匹配优先，再允许明确标识的前缀候选。find_related_symbols输入symbol_id、relation（extends/implements/extended_by/implemented_by）、limit（默认10、最多20）。

Java解析关系依次使用显式限定名、单类型import、同包候选；通配导入和同名多目标保留候选集合。Python仅在基类表达式是Name/Attribute且能由模块/导入关联时提供目标候选，其他标unresolved。关系标识只表示声明关联，不解析方法调用接收者、泛型绑定、注入优先级、运行时代理或Lombok生成成员。反向关系按这些声明建立。

签名/注解线索每条最多300字符，每符号最多10条导入/注解摘要，超限标截断，避免把整文件塞进工具响应。XML/YAML/properties保持有排名的文本检索；Mapper方法与XML映射由模型读取实际证据解释，不把它包装成已实现的框架语义分析。

替代方案：正则难以可靠处理重载、内部类和多行声明；完整语言服务器/编译器增加构建环境和依赖，超出本阶段静态只读范围。

### 4. 可解释的文本与标识符排序

search_code_ranked使用任务内文件文本，按最多80行、20行重叠切成候选片段（每片段最多8000字符，保持完整行；单行超限跳过该行并记录）。Java/Python符号用于增加匹配线索，其他允许类型采用相同文本片段。不会把未解析文件直接丢弃。

初始规则version=1：保留完整标识符并拆分camelCase/snake_case，统一小写；中文连续文本使用二元字符片段，单字保留。采用BM25（k1=1.2,b=0.75）文本分数，加完整符号名精确匹配3分、完整查询在路径中匹配1分。词频、文档频率和平均片段长度由当前索引计算，空查询项不计分。纯中文概念未出现在源码时可能无匹配，不宣称embedding语义召回。

同一(path,start,end)去重，按总分降序、path/start/end升序稳定排序；重叠片段不是独立文件。只返回正匹配结果，top_k默认5、最多20；每条摘要最多400字符、整个摘要预算4000字符，超出则截断并标注。返回BM25/符号/路径贡献用于调试，不承诺分数是概率。

替代方案：embedding会增加服务、索引版本和评测变量；此阶段先把可解释词法基线做扎实。对中文概念改写仍依赖模型，真实失败分类应能暴露这一限制。

### 5. 与LangGraph及记录的接入

将全局TOOLS的使用改为按任务模式创建不可变工具定义和匹配的执行白名单；literal的顺序、schema和现有提示行为保持一致，indexed增加简短导航说明。模型节点、repair、上下文字符计算必须使用同一工具集合，执行层独立拒绝未启用工具。

新增工具仍返回ok/data或ok/error，计入工具次数；工具元数据包括稳定候选和独立diagnostics。重复签名/结果比较只使用语义结果及内容版本，排除耗时、随机实例ID和累积计数，防止每次建索引统计变化绕过重复拦截。原invalid JSON、批量skipped、一次修正和上下文超限行为继续回归。

trace增加retrieval_setup事件，记录模式、算法版本、解析器版本和参数；每次检索事件记录排名候选、索引范围、耗时、截断和错误。索引初始化不虚增模型次数。最终回答沿用findings/citations/uncertainties，不引入新的无法证实的调用图字段。

### 6. 分析报告与只读输出边界

新增reporting.py纯函数从Result及trace渲染Markdown，包含问题、事实/文件行引用、证据摘要、未确认事项、停止原因及执行统计。渲染不二次调用模型；失败任务保留停止原因而非生成“成功总结”。使用records.py相同的临时文件、fsync和原子替换机制，写入失败退出2。

新增报告和原trace写入均在执行前解析目标路径及现有父目录链接，若落在被分析root内则拒绝。此兼容变化明确写入README：分析CodeTrace自身时输出到仓库外目录。输出内容不保存环境密钥、供应商异常正文；仍可能包含用户主动分析的源码，保存由用户显式选择。本阶段不处理恶意并发替换文件系统的OS级防护。

不将三个项目复制进CodeTrace。新增benchmarks目录只保存仓库清单、原创标注、来源说明和报告；本地路径映射单独由CLI参数 --repo-map 提供，不写绝对路径到公共基准配置。仓库由开发者准备在目标根目录外的独立路径。基准运行器只读检查Git身份、完整提交号和允许文件内容；其Git命令使用固定参数列表、不执行仓库钩子或构建，内容仍由安全读取层提供。

每仓库至少8题：入口1、跨文件2、配置1、异常2、无答案2；含同名符号/多实现问题。每题记录预期事实、必需证据组（允许等价文件/范围）、允许不足和适用范围。标签由实际阅读固定提交后编写，不凭项目名预填答案。每个仓库至少20个可读源文件，首次清单检测不足或范围冲突时必须报告原因并调整提案，不能静默换仓库。

v2数据将repo_id与本地路径分离，明确source_manifest、split和case记录；可读文件清单只含既有允许范围，排除凭证和构建产物（target及虚拟环境变体作为新增索引排除配置，literal保持原规则）。对照两模式使用相同已固定的基准源码范围，发现原模式额外扫描产物需先在基准副本准备阶段清理并验证，不能把不同输入范围包装成排序收益。提交号相同但允许源码已修改时也拒绝；缺文件、脏源码、路径别名到同一仓库、伪造不同repo_id都需检测。

开发题可用于调参，mall-tiny保留题在规则/提示冻结后首次运行。标注者可以预先阅读保留源码编写答案，但保留运行结果不能用于调参而仍声称未见验证。冻结点记录代码提交、数据集摘要、模型参数、工具/提示摘要与排名版本。此划分测试项目实现的跨仓库适应性，不证明基础模型从未见过公开代码。

### 8. 成对评测、分批执行与人工审核

保留旧evaluation.json及v1读取行为；新v2报告含planned/ran/reviewed数，按case×mode保留全部48个组合，包括not_run、failed和insufficient。默认仍offline，真实模式需--live；--max-runs默认4，每个组合是一个任务，不是一个模型请求。支持--case-id、--variant literal|indexed|both、--resume REPORT。先冻结数据/配置再执行，任务轮数/工具数/超时/上下文默认沿用现值，两个模式相同。

恢复要求数据摘要、仓库版本、模型及非秘密配置、预算、程序/工具/提示/算法摘要一致，凭证值不进入摘要。已完成组合不重跑；--retry-failed显式重试保留attempt历史及费用，分数默认按最新指定attempt且报告全部尝试，避免挑最好结果。每次结束原子保存进度，单题异常继续到该批次限额；进程中断后的未完成项不自动视为成功。

能力对照只把question提供给模型。gold文件、片段和facts不进入任何真实消息或检索参数。新增独立检索测试可提供固定query用于测候选Recall@5，但明确是组件指标；在线最终问题不附参考查询。离线模式只测路由/工具/记录，不能生成语义成功率。

literal/indexed对照同时改变可用工具、索引范围上限和检索方式，属于整体方案比较；不能把所有差异归因于BM25或符号解析。组件排名测试须使用相同候选文件集合；若要宣称某单项功能的因果收益，需要另做只改变该项的消融实验，本阶段不作该类未经验证的宣传。

逐题计算预期证据组文件覆盖、引用有效率、人工事实正确/遗漏/合理拒答、调用次数、总耗时及服务端usage；答案语义成功要求有答案题completed且事实正确无关键遗漏，无答案题insufficient且拒答合理。实际运行失败计失败，未运行/未审核使完整成功率保持null，同时显示完整计划分母、已执行数和审核数。无引用不算100%，无usage不记零成本。汇总可给小样本中位数/最大值及题级差异，不宣称延迟SLA或统计显著。

人工审核v2绑定report_id/case_id/mode/run_id/数据摘要，记录reviewer和review_source。AI可辅助生成审核草稿，review_source=assistant_draft不能算已人工确认；只有用户或指定人工审核者确认的human记录满足门槛。负面结果不得删题或改标签提升分数，标注纠错需升数据版本并重新比较。

### 9. 分析验收和后续编程路线图

分开记录两个状态：
- implemented：本变更全部离线功能、文档、测试及要求的实测报告已交付。缺真实数据/人工审核时保留对应任务未完成，不能拿离线模拟代替。
- analysis_ready_for_programming：至少24题×2模式全部执行及人工审核；indexed整体>=18/24，保留集>=6/8（扩大数据集后按75%）；无已知未修复的边界/引用回归；indexed语义成功数不低于literal。同一报告给出效果和成本变化，即使没有净收益也如实说明。

75%是此次提案的阶段目标，不是当前成绩、招聘通过线或统计保证。未达标时可以完成准确的失败报告，但不标记ready；后续调优形成新工作，不能为了勾完当前任务无限扩功能或自行放宽标准。完成旧MVP的剩余smoke与10题真实报告仍分别核实，可引用相同有效证据但不自动勾选旧任务。

未来路线（仅规划，不在本次tasks中实现）：
1. 以分析结果生成修改建议：目标文件、理由、约束、验证方法，先形成可审查方案。
2. 针对一种任务生成有限补丁，例如参数校验及对应测试；需要独立工作区和变更范围约束。
3. 在限定环境运行预定测试，根据失败反馈做有限修正，输出diff、测试记录及回退信息。

进入下一阶段仍需独立propose/apply。届时再确定支持语言、任务种类、隔离方式、命令策略、重试与回退、人工审查边界；这些决策不影响本次只读分析实施，故仅记路线图。

## Risks / Trade-offs

- [解析依赖在Windows不可安装] → 前置兼容性验证并锁定版本；无法满足时报告阻塞，literal继续可用，不静默改成不可靠正则。
- [静态关系被误认为运行调用] → 工具标明candidate/ambiguous/unresolved，最终引用仍读源码，加入多实现/动态注入负例。
- [词法排序对中文概念弱] → 真实错误分类明确暴露，允许模型改写；不承诺语义召回，未来是否加入embedding由报告决定。
- [索引与指纹重复IO增加延迟] → 同时记录构建/查询/总耗时，先验证复用收益；暂不引入复杂持久缓存。
- [标注或保留集泄漏] → 哨兵测试、按仓库划分、冻结记录、披露开发使用；公开代码不能证明模型预训练未见。
- [真实评测费用与服务不稳定] → 显式live、默认4任务一批、兼容续跑、保留失败和usage，无模型调用发生在默认CI。
- [目标规模过大] → 资源上限与partial报告，不以扩大预算掩盖定位失败；实现验收与质量门槛分离。
- [人工审核未到位] → 未审核指标保持null，审核草稿不能冒充human，相关任务继续待验收。
